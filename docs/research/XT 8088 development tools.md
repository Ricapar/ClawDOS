# Build a real toolchain on the XT

A usable self-hosted toolchain for the XT exists, and almost all of it can legally ship on the ClawDOS image. **TinyASM** (BSD-2, NASM syntax, its author says it runs on a real PC XT in 128 KB) and **Wolfware Asm** (MIT) can replace the DEBUG-script workflow for .COM programs. **JWASMR + WarpLink** add MASM-syntax OBJ/EXE builds. **Pacific C** is the only ANSI C compiler HI-TECH explicitly allowed to be redistributed. **GW-BASIC** (TK Chia's MIT rebuild of Microsoft's source) and **F-PC Forth** (public domain) are the interpreters. **lDebug** handles scripted debugging, and the **GNUish** 16-bit GNU tools (sed, grep, diff, patch, awk, textutils) cover text processing. The catch is that very little of this is proven on an 8088. Only a handful of tools have an author's or vendor's 8088/XT statement or an 8086-only timing run behind them. Pacific C, the GNUish binaries, Info-ZIP, 4DOS and WarpLink are all inferred to work, and none has been tested by this project. Speed is the other limit. On the one consistent benchmark (a 2000-line assembly source, estimated at 4.77 MHz), times range from **about 5 s (A86) to about 7 min (NASM)**, and Turbo C 2.0 builds Hello World in about 8 s where Turbo C++ 1.0 takes 87 s. Tool choice therefore decides whether the agent waits seconds or minutes per build. The user's original disks open a stronger second tier: **Turbo C 2.01, MASM 5.1, Turbo Pascal 5.5–7.0 (TPC), QuickBASIC 4.5 and Microsoft C 6.0** all have documented or strongly indicated 8088 support. Several popular "DOS" tools are 386-only and must stay off the image, among them FASM, NASM 2.x, Open Watcom's DOS host, DJGPP/ia16-gcc, Smaller C, FreeBASIC/Free Pascal, Borland C++ 3.x, MASM 6.x and FreeDOS 1.4's own UNZIP.

**How to read the status labels.** **Confirmed** means a vendor or author document states 8088/XT support, or the tool ran in an 8086-only cycle measurement or on 8088 hardware in a cited report. **Likely** means strong circumstantial evidence, such as an 8088-era assembly codebase or an XT-era product. **Unconfirmed** means no evidence either way. **Excluded** means a source says the tool needs a 186, 286 or 386. Nothing in this report has been run on 86Box or on the user's XT yet. Licence classes follow the brief: (a) free/OSS and redistributable, (b) freeware/shareware that may be redistributed under conditions, (c) free to download but redistribution not granted or unclear, (d) commercial, needing an original copy.

## The agent's interface favours a few tool traits over raw power

The `run` tool gives one command line of about 120 characters (DOS caps it at 127), no keyboard and captured stdout. Four tool properties follow from that and outweigh feature lists.

**The tool must not open a full-screen UI or wait for keystrokes.** That rules out D86, Insight, AFD, every IDE (TC, PPD, TURBO.EXE) and every screen editor for agent use. Those tools stay useful for the human at the keyboard.

**The tool must not hang at end of input when driven by redirection.** FreeDOS DEBUG explicitly "will not hang if it reaches an end of file before encountering a `q`" ([Debug/X GitHub](https://github.com/Baron-von-Riedesel/DOS-debug)). MS-DOS DEBUG makes a trailing Q "crucial" ([MSDebug manual](https://pushbx.org/ecm/doc/msdebug.htm)), so the existing workflow should stay on the FreeDOS binary.

**Output should reach DOS stdout.** Programs that write straight to video memory never reach the capture. Examples are Turbo Pascal's CRT unit and GW-BASIC's LOCATE/COLOR/SCREEN statements (unverified for both; see the verification list).

**A non-zero exit code on error is valuable.** TinyASM documents one ([tinyasm](https://github.com/nanochess/tinyasm)).

The command-line cap is easy to work around. The agent already has file read/write tools, so it can write a `BUILD.BAT` or a linker response file and `run` that. A batch file is also a better build driver than MAKE on 640 KB. MAKE stays resident while it spawns the compiler, and that memory cost is why a FreeDOS kernel build on an 8086 ran out of RAM ([bttr forum](https://www.bttr-software.de/forum/forum_entry.php?id=16359)). For the same reason, editors matter little to the agent. Writing a whole file is more reliable than an EDLIN script full of ^Z and ^V control characters.

EMS (from the PicoMEM's LIM driver) helps less than hoped. None of the shortlisted compilers or assemblers is documented as using it. The two EMS mentions in the notes are the SEDT editor, which loads large files "using disk or EMS" ([BTTR text editors](https://www.bttr-software.de/freesoft/txtedit1.htm)), and the NASM 8086 rebuild's author suggesting EMS support "may be needed". An EMS RAM disk for compiler temporary files is the most plausible way to use it, but no benchmark exists.

## Assemblers range from 5 seconds to 7 minutes on the same source

The single most useful data point is one bttr-software thread. It estimated assembly times at 4.77 MHz from 8086-only cycle counts for a roughly 2000-line source (PSR Invaders), and it caught tools that use 186+ opcodes ([bttr timing thread](https://bttr-software.de/forum/mix_entry.php?id=23405)). **A86 4.05 took about 5.4 s, Wolfware Asm about 42 s, as86 about 50 s, MASM 5.10 about 55 s, a72 about 108 s, WASMR/JWASMR about 4–4.5 min, MiniNASM about 6 min and NASM16 about 7 min.** These are estimates, not wall-clock times on a real XT with a real disk, but the ranking is what matters. At the scale of the agent's current DEBUG programs (tens of lines), every assembler here finishes in seconds.

In practice, **TinyASM is the natural successor to DEBUG scripts**. Its syntax is standard NASM, which the agent knows well, and it produces .COM files directly with listings and exit codes. Wolfware is the faster MIT alternative. JWASMR is the route to multi-module EXEs and to MASM-syntax code from books and magazines. A86 is the speed outlier. It is about eight times faster than Wolfware and fifty times faster than JWASMR, and the user could reasonably pay for it, but its idiosyncratic syntax and registration requirement keep it out of a free image.

## Linkers, debuggers and MAKE are thin but adequate

**WarpLink** is the strongest free linker. Michael Devore released it to the public domain with source, it supports overlays, and ecm made a new release in September 2025 ([WLMAN.DOC](https://pushbx.org/ecm/doc/WLMAN.DOC); [phatcode](https://www.phatcode.net/downloads.php?id=476); [pushbx blog](https://pushbx.org/ecm/dokuwiki/blog/pushbx/2026/0204_chasing_a_warplink_bug)). Its 8088 status is only **likely**, inferred from its 1989–93 assembly codebase. **VAL** is a small free 16-bit-only linker ([OSDev wiki](https://wiki.osdev.org/VAL)), but its licence text was not found, so it sits in (c) until checked. ALINK's host CPU is unknown. TinyASM, A86 and NASM all emit .COM files without a linker. No free 8088 librarian and no verified free EXE2BIN were found.

For debugging, **FreeDOS DEBUG** (Vojta / Debug/X) defaults to the 8088. Its 386 features (`rx`, 32-bit registers, `dx`) are optional, and its licence is "copyrighted, but feel free to distribute and use it as you wish" ([DEBUG README](https://sunsite.icm.edu.pl/packages/freedos/dos/debug/vojta/1.25/README.TXT)), effectively class (a). **lDebug** is the upgrade. It runs script files with the Y command, does not "crash or loop infinitely upon encountering the end of a stdin-redirected file", has an expression-aware assembler with SHORT/NEAR/FAR control, and is under the Fair License ([lDebug manual](https://pushbx.org/ecm/doc/ldebug.htm)). Its releases are "intended to run on any processor type down to the 8088/8086" ([bttr announce](https://bttr-software.de/forum/mix_entry.php?id=17816)). **Insight** is GPL v2 and real mode, but it is full-screen and its CPU minimum is unconfirmed. **DEBUGX**, the DPMI build, is useless on an XT.

No free MAKE was confirmed to run on an 8088. GNUish lists 16-bit-era **GNU make 3.71 and dmake 3.8** ([GNUish](https://ftp.lip6.fr/pub/freedos/gnuish/gnuish.htm)), but their bitness and 8088 status are unconfirmed, and the resident-MAKE memory problem above argues for batch files anyway. Dunfield's **DdsBuilDer** (DBD.ZIP, 22.3 KB) is a build helper for Micro-C ([Dunfield downloads](https://dunfield.themindfactory.com/dnld.htm)).

## C is the weakest free category, so Pacific C is the critical test

No free C compiler is documented to run on an 8088. The best candidate is **Pacific C**, an ANSI C compiler for DOS with a command-line driver, `PACC.EXE`. In 1998 HI-TECH wrote: "Permission is hereby granted to use Pacific C for the FreeDOS project or any other private or commercial use", and it "may be redistributed alone or with other software providing the complete package is distributed and the copyright notices remain intact" ([FreeDOS mirror readme](https://rsync.rediris.es/mirror/freedos/files/devel/c/pacific/readme.txt)). The freeware V7.51 readme supports x87 code but states no CPU, RAM or disk requirement ([freeware readme](https://ftp.icm.edu.pl/packages/freedos/devel/c/pacific/freeware/readme.txt)). It is class (b) on the condition that the archive ships unmodified. The 1998 grant predates V7.51, so which version it covers is slightly ambiguous. Its 8088 status is **unconfirmed**, and testing it is the highest-value item on the verification list.

**Dunfield Micro-C** (MCDOS.ZIP, 220.6 KB, with source) is "released for anyone to use for any reasonable purpose", with attribution asked for in published material ([COPY.TXT](https://dunfield.themindfactory.com/dnld/sc/COPY.TXT)). The notice doesn't mention redistribution explicitly, so it falls in (a)/(b). It targets the 8086 family, runs on IBM PCs, and needs a MASM-compatible assembler and linker ([mc315pc.txt](https://sunsite2.icm.edu.pl/packages/freedos/devel/c/micro-c/mc315pc.txt)). Its 8088 status is **likely**. It is a K&R-ish subset compiler, fine for utilities but poor for porting ANSI code. The TASM.ZIP on Dunfield's page is Borland code with its own README, so don't assume it can be shipped. **Dev86 BCC** has a 16-bit OpenWatcom-hosted DOS build that produces tiny/small-model 8086 assembly under the GPL ([bttr](https://www.bttr-software.de/forum/mix_entry.php?id=23110)). It is **unconfirmed**, because it runs on an 8088 only if it was built with `-0`. **DeSmet C88** reportedly went GPL in 2005 and emits strict 8086 code ([Slashdot](https://developers.slashdot.org/story/05/08/03/1810211/old-c-compiler-lives-again-under-gpl); [Usenet 1988](https://www.tuhs.org/Usenet/comp.lang.c/1988-November/043352.html)), but its archive and licence text were not located. **Smaller C is excluded**: it "generates 16-bit and 32-bit 80386+ assembly code" ([SmallerC](https://github.com/alexfru/SmallerC)), so even its 16-bit output won't run on an 8088. Open Watcom, DJGPP and ia16-gcc ("on a DJGPP host") need a 386 to host ([FreeDOS devel](https://sunsite.icm.edu.pl/packages/freedos/repositories/latest/pkg-html/group-devel.html)). They remain the right cross-compilers on the PC, which is how this repo already builds.

Turbo C is free to download but cannot be shipped. Borland's antique-software notice allows "personal use only" and keeps the copyright notices "still in force" ([Embarcadero item 26014](https://cc.embarcadero.com/Item/26014), via search-indexed text). A quoted version adds that the files "may not be made available via the Internet or any hard copy media" ([Delphi-PRAXIS repost](https://www.delphipraxis.net/27397-post18.html)). That makes the download class (c), and the user's own disks are the clean route.

## Interpreters and other languages give the agent instant feedback

Interpreters skip the compile-link cycle, which is worth more at 4.77 MHz than anywhere else. **GW-BASIC** is the standout. Microsoft released the 8088 assembly source under MIT in 2020 without binaries ([Wikipedia](https://en.wikipedia.org/wiki/GW-BASIC)). TK Chia assembles it with JWasm/MASM under MIT, and the latest "Stable" release is 20261005 (GWB26A05.ZIP, 76 KiB). Serial I/O is missing, and printer, joystick and light pen "need more testing" ([Codeberg releases](https://codeberg.org/tkchia/GW-BASIC/releases); [GitLab](https://gitlab.com/tkchia/GW-BASIC)). The FreeDOS book points users to this build ([FreeDOS book](https://freedos.org/books/get-started/21-gw-basic/)). GW-BASIC documents `GWBASIC PROG >file` redirection of PRINT output ([Scribd transcription](https://www.scribd.com/document/378780455/basic4); [Kaypro user guide](https://kayprojournal.com/images/7/7d/GW-Basic_UG_3.2.pdf)). The agent pattern would be `GWBASIC P.BAS >O.TXT`, with `SYSTEM` as the last line. Its 8088 status is **likely**, since the source is 8088 assembly, but the rebuild's 8088/FreeDOS behaviour and real stdout capture are unverified.

**F-PC 3.6** is "a public domain package" ([Internet Archive](https://archive.org/details/fpc-36)), "optimized for IBM-PC, XT & AT machines running DOS" ([GitHub uho/F-PC](https://github.com/uho/F-PC)). It is class (a) and **likely** runs on an 8088. Batch-mode load-and-exit is unconfirmed.

**A.D.A. PD Prolog 1.9x** is a 1986 "public domain", "rather slow" DOS Prolog ([CMU AI repository](http://www.cs.cmu.edu/afs/cs/project/ai-repository/ai/lang/prolog/impl/prolog/pdprolog/0.html)). It is class (a)/(c) and likely runs.

**XLISP 2.1e** ships IBM PC executables ([CMU](https://www.cs.cmu.edu/afs/cs/project/ai-repository/ai/lang/lisp/impl/xlisp/0.html)). XLISP-PLUS is "only distributed for non-commercial (or educational) use" ([almy.us](https://almy.us/xlisp.html)), which puts it in (b)/(c) pending its licence file. Betz's XLISP 3.0 is MIT ([GitHub](https://github.com/dbetz/xlisp)), but its 8088 fit is unknown.

**FST Modula-2 4.0** is "closed source freeware" ([EDM2](https://www.edm2.com/index.php/Fitted_Software_Tools_Modula-2)). It is class (b)/(c) because its redistribution terms were not seen, and its 8088 status is unconfirmed.

**Bywater BASIC** is open source (GPL v2 in FreeDOS), but one report says it "needs a BIG stack… so 16bit stuff is out" ([VirtuallyFun](https://virtuallyfun.com/2010/06/09/bywater-basic/)). A `bccdos16.bat` in one mirror hints at a 16-bit target ([GitHub](https://github.com/John-Titor/bwbasic)). Treat it as **unconfirmed**. A Watcom `-0` large-model build in this repo is the cheapest way to find out.

**PowerBASIC 3.5** is sent free on request but is "not freeware" and may not be redistributed ([bttr forum](https://bttr-software.de/forum/forum_entry.php?id=22536)), which makes it (c).

**FreeBASIC and Free Pascal are excluded.** They are DJGPP/386 hosted, and Free Pascal's i8086 target is a cross-compiler only (both from background knowledge, consistent with the FreeDOS devel listing). Logo, Icon, Little Smalltalk, REXX (Regina is believed to be DJGPP) and Lua were not researched.

## Editors and text utilities come mostly from GNUish and the FreeDOS base

The **GNUish MS-DOS** project "was first organized with small IBM PC's in mind, that is, 8088 and 80286 based systems", and its software "will run on 8086 and 80286-based machines; a 80386 not required" ([GNUish lip6](https://ftp.lip6.fr/pub/freedos/gnuish/gnuish.htm); [GNUish riken](https://ftp.riken.jp/GNU/MicrosPorts/MSDOS.gnuish)). It provides sed 1.06, grep 2.0, diff 2.3, patch 2.x, mawk 1.2.2, 16-bit gawk, textutils 1.11 (sort, head, tail, wc, uniq, cut, od, md5sum), less, m4, RCS, indent, flex, bison, uuencode, gzip 1.2.4, tar, zoo, bc and Info-ZIP UnZip 5.32 / Zip 2.2. All are GPL v1-or-later, so **the source must ship with the binaries or be offered in writing**. Their status is **likely**. The project's claim is blanket, and individual builds may have been compiled for a 286 (MSC `-G2`), so each binary needs a test. The archive also mixes in 32-bit builds: gawk 3.0.x ships both `gawk.exe` (16-bit) and `gawk-djg.exe` (32-bit), so pick the 16-bit file. BTTR's guidance agrees: 16-bit builds "work on 80286 or older CPUs", while DJGPP builds of bash, shellutils, findutils and sharutils need a 386 and DPMI ([BTTR Unix-like](https://bttr-software.de/freesoft/unix.htm)). "There is no port of GNU bash available to 8088 and 80286 systems" ([GNUish](https://ftp.lip6.fr/pub/freedos/gnuish/gnuish.htm)). The **Berkeley Utilities** (awk, grep and others) are "now in the public domain" ([BTTR](https://bttr-software.de/freesoft/unix.htm)), but their CPU is unstated.

**Archives:** do not rely on FreeDOS 1.4's `unzip`, which the 1.4 report tags "386+" alongside JEMM, HIMEMX, FDXMS, LBACACHE and SHSUCDX ([FreeDOS 1.4 report](https://www.ibiblio.org/pub/micro/pc-stuff/freedos/files/distributions/1.4/report.html), read from a search snippet). Ship the 16-bit Info-ZIP builds instead. Their licence permits use "for any purpose" provided the copyright notice is reproduced ([Info-ZIP License](https://infozip.sourceforge.net/license.html)). Which UnZip 6.0 / Zip 3.0 16-bit builds exist is unverified, so use UnZip 5.32/5.52 as the safe fallback. PKZIP 2.04g, LHA 2.55 and ARJ 2.x are believed to run on an 8088, but their licences were not fetched, so treat them as (c).

**Shell:** **4DOS** source is under a modified MIT licence that bars commercial use and compiling "for use on any operating system other than FreeDOS" ([Wikipedia: 4DOS](https://en.wikipedia.org/wiki/4DOS)). That fits this image, but its 8088 status on 7.50/8.00 is **unconfirmed**. If it works, its stderr redirection (`>&`), `IFF`, `DO` loops and `%@functions` would make each 120-character `run` call far more expressive.

**Editors:** the 1.4 report tags EDLIN and EDIT "all" ([FreeDOS 1.4 report](https://www.ibiblio.org/pub/micro/pc-stuff/freedos/files/distributions/1.4/report.html)). An 86Box issue, though, says FreeDOS EDIT and MEM lock up an emulated 8086/8088 ([86Box #249](https://github.com/86Box/86Box/issues/249)), so "all" means "should work, test it". FreeDOS maintainers say the kernel and FreeCOM run on an 8088 but not every bundled program does ([VCFed](https://forum.vcfed.org/index.php?threads/freedos-on-8088.42683/)). For the human, **VDE** is about 80 KB of assembly and "copyrighted freeware" that "may be freely used and distributed in complete original form". It is class (b) and needs DOS 3.x+, with an "8088- & Palmtop-friendly" 1.65C release ([VDE manual](https://sites.google.com/site/vdeeditor/Home/vde-files/vde-1-96-manual); [BTTR editors](https://www.bttr-software.de/freesoft/txtedit1.htm); [archive.org vde-197](https://archive.org/details/vde-197)). SuperTED 1.01 (6 KB) and GNUish's 16-bit JED, Freemacs and MicroEmacs are alternatives. The common DOS builds of Vim and TDE are 32-bit ([BTTR editors](https://www.bttr-software.de/freesoft/txtedit1.htm)). FreeDOS FC (`/B`, `/N`), FIND and SORT are useful agent primitives, though their per-tool CPU tags were not readable.

Do not install from your disks: **Turbo C++ 3.0 / Borland C++ 3.x** (reported to need a 286 ([Tech Monitor](https://www.techmonitor.ai/?p=165824)); the command-line real-mode variant is unverified), **MASM 6.x** (needs DOS 3.0+/3.3+ and 640K ([MASM 6.0 guide](https://ftp.mirrorservice.org/sites/www.bitsavers.org/pdf/microsoft/masm/Microsoft_MASM_6.0_1991/Installing_and_Using_the_Professional_Development_System_Ver_6.0_Feb91.pdf); [MASM 6.1](https://ftp.mirrorservice.org/sites/www.bitsavers.org/pdf/microsoft/masm/Microsoft_MASM_6.1_1992/MASM_6.1_Getting_Started_1992.pdf)), but ML.EXE is believed DOS-extended), **TASMX/TPX/BP** (they need memory above 640K), **TASM32** (Win32) and **CodeView** on the XT. Several products are worth checking your shelf for, but none was researched beyond a name: MKS Toolkit 1.x/2.x (vi, awk, sed, a Korn shell), Lattice C, Aztec C86, Mix Power C, Zortech C++, Turbo Basic 1.x, Turbo Prolog, Logitech Modula-2, Brief, QEdit, PE2 and Norton Utilities 4.x.

## Recommended starter set, optional tier and test plan

**Starter set (free and redistributable, all small).** Install in this order:

1. TinyASM (BSD-2) as the primary .COM assembler.
2. Wolfware Asm (MIT) as the faster second assembler.
3. JWASMR (OWPL) and WarpLink (public domain) for MASM-syntax OBJ/EXE builds.
4. lDebug (Fair License) alongside the existing FreeDOS DEBUG.
5. Pacific C (complete unmodified archive with its readme), conditional on passing its 8088 test.
6. Micro-C (MCDOS.ZIP, with the COPY.TXT attribution) as the fallback C.
7. GW-BASIC from TK Chia (MIT, 76 KiB zip; include LICENSE).
8. F-PC 3.6 (public domain).
9. GNUish 16-bit sed, grep, diff, patch, mawk and textutils 1.11, with their source archives to satisfy the GPL.
10. Info-ZIP 16-bit UnZip/Zip (keep the licence file).
11. VDE for the human (unmodified archive).
12. 4DOS (FreeDOS-only licence), if it passes on an 8088.

The notes give sizes only for MCDOS (220.6 KB), GW-BASIC (76 KiB), VDE (about 80 KB) and DdsBuilDer (22.3 KB), but every item is a 1980s–90s 16-bit tool. The set should fit in a few megabytes, with the GPL source archives likely the largest part. Measure the total when building the image.

**If you own these disks:** Turbo C 2.01, Turbo Pascal 5.5–7.0 (TPC only), MASM 5.1 (with LINK/LIB), TASM 2.x/3.x, QuickBASIC 4.5, and MS C 6.0 if 8–20 MB of disk can be spared. Install them from your originals onto your own image, never onto a shipped one. **Optional paid upgrade:** A86 (shipping the unmodified ZIP is allowed, but you must register to keep using it, $52) for roughly 8–50× faster assembly than the free assemblers.

**Must be verified on 86Box (8088) or the real XT before shipping.** The project's DOSBox-X boottest runs as an 80186 for networking, so it cannot catch 186 opcodes. Use 86Box with an 8088 machine (`scripts/run86box.py` plus `--autotest` batch files) as the authority.

1. **Pacific C** `PACC` on an 8088: does it run, which memory models work, how much RAM it needs, and compile time for Hello World and a 500-line file.
2. **TinyASM, Wolfware, JWASMR and WarpLink**: run each, record real wall-clock times from the PicoMEM SD image, and test whether JWASMR's memory limits bite on modest sources.
3. **GW-BASIC (TK Chia)**: runs on an 8088 under FreeDOS, `PRINT` reaches redirected stdout, and `SYSTEM` exits cleanly with no keyboard wait.
4. **Every GNUish binary**: confirm it isn't built for a 286 (`-G2`). Run each once, and pick the 16-bit gawk rather than `gawk-djg`.
5. **lDebug**: Y-script and redirected-stdin behaviour, plus the existing FreeDOS `DEBUG < script` path on real hardware.
6. **FreeDOS EDIT and MEM**: the reported 8086 lock-up ([86Box #249](https://github.com/86Box/86Box/issues/249)), and the CPU tags of FC/FIND/SORT once the 1.4 `report.html` can be read in full.
7. **4DOS 7.50/8.00, Info-ZIP 16-bit, F-PC batch mode (load, run, exit) and Dev86 BCC 16-bit.**
8. **Licence texts inside each archive** before inclusion: the Pacific C version covered, TK Chia's LICENSE file, VDE, Arrowsoft, VAL, XLISP and FST Modula-2.
9. **From your disks**: TASM.EXE and QuickC/MS C 5.1 on the 8088, and whether TP's CRT unit and GW-BASIC screen statements bypass stdout capture.

## Conclusion

Free and commercial tools are not neatly split by power on this machine; the split is by speed. The free toolchain is credible but slow: JWASMR takes minutes where A86 takes seconds, and the only free ANSI C is unbenchmarked. The commercial tools the user already owns, especially Turbo C 2.01 and Turbo Pascal's TPC, are what turn the XT into a machine where an agent can iterate several times per minute. The practical strategy is therefore two images. A shipped image carries the verified free set, with TinyASM replacing DEBUG scripts as the default path. The user's personal image adds the Borland and Microsoft compilers from original disks. The agent's interface also changes the usual ranking of tools. Exit codes, stdout fidelity and EOF-safe stdin handling matter more than IDEs or optimisers, and batch files written by the agent stand in for MAKE.

The largest open risk is not licensing, which is mostly settled, but the gap between "16-bit" and "8088". Several sources show tools quietly built for a 186 or 286 (official NASM 16-bit, AP.EXE, possibly GNUish MSC builds), and the project's DOSBox-X test harness runs as an 80186. Until a cheap 8088 smoke test exists, any tool on the image is a guess. The first engineering task should be an 86Box autotest batch that runs every shipped tool once and logs pass/fail to COM1.
